# 5.1 Payment intake

Goal: accept a payment request safely. Money starts to move only in 5.2.

## Build

- `services/switch-service` on port 7006, database `switch.db`, migrations in `migrations/001_switch.sql`.
- Gateway route `/api/switch` for customers and staff. `/internal/*` stays hidden.
- `POST /pay` for customers. It requires `Idempotency-Key` and this body:

  ```json
  { "payerVpa": "asha@kosh", "payeeVpa": "ravi@alpha", "amount": 50000, "note": "rent", "mpinToken": "..." }
  ```

  The checks run in this order:
  1. zod validation. `amount` must be a positive safe integer in paise. Both VPAs must look like `handle@psp`.
  2. Amount limit (`SWITCH_MAX_TXN_PAISE`). Payer and payee VPA must differ.
  3. MPIN token verified with identity `POST /internal/mpin-tokens/verify`. It must belong to the caller and have purpose `PAYMENT`.
  4. Payer VPA resolved, and its `userId` must be the caller. Payee VPA resolved. Errors come back as `PAYER_*` / `PAYEE_*`.
  5. One transaction does three things: consumes the token `jti`, creates the `txns` row with an RRN, and emits `TxnInitiated`.

  The response is `202` with the customer view (`id`, `rrn`, `status`, `state`, ...). Replaying with the same key and the same fingerprint returns the stored response with `idempotent-replayed: true`.
- `GET /txn/:id`: payer or payee get the customer view, SWITCH_OPS gets the ops view, anyone else gets 404. `GET /txns` lists the caller's own payments.
- RRN: 12 digits, `Y DDD HH NNNNNN`, in IST (`src/rrn.ts`).

## Tests

- `test/intake.test.ts`: acceptance, double click, replay after token expiry, key reuse with a different body, per-user key scope, single-use token, token problems, body validation, caller checks, VPA ownership and payee errors, status visibility.
- `test/units.test.ts`: RRN format, IST rollover, uniqueness.
- `tests/e2e/phase-5.1.test.ts`: the same rules through the real gateway, identity and vpa-service.
