# switch-service decisions

One line per decision the spec left open. Format: `- <date> <sub-phase>: <question> -> <choice> because <reason>`.

- 2026-11-18 5.1: the sub-phase files 5.1-5.5 linked from docs/phase-5/README.md did not exist -> scope taken from DEV_PLAN.md Phase 5 plus the handbook's README, and short sub-phase files were written afterwards to describe what was built, because the README is the only binding spec.
- 2026-11-18 5.1: how does the switch know the payer owns the payer VPA -> vpa-service `GET /resolve/:address` now also returns `userId` to service callers (customers still never see it), because the owner was already in vpa.db and a second endpoint would duplicate the resolve and cache logic.
- 2026-11-18 5.1: is an MPIN token single-use -> yes, the switch stores each token `jti` in `used_mpin_tokens` inside the same transaction that creates the payment, because identity tokens are valid for 120 s and a replayed token must not authorise a second payment.
- 2026-11-18 5.1: what does the idempotency fingerprint of `POST /pay` cover -> `payerVpa, payeeVpa, amount, note` but not `mpinToken`, scoped per user, because a client retrying after its token expired must get the stored answer, not a 401 or a second payment.
- 2026-11-18 5.1: does `POST /pay` wait for the saga -> no, it answers 202 with the INITIATED view and the saga starts in-process right after; clients poll `GET /txn/:id`, because the gateway timeout (10 s) is shorter than a DEEMED resolution.
- 2026-11-18 5.1: RRN format -> 12 digits `Y DDD HH NNNNNN` (last digit of the IST year, IST day of year, IST hour, 6-digit sequence per hour from `rrn_counters`), because it is unique, sortable and matches the 12-digit UPI RRN length.
- 2026-11-18 5.1: payer and payee VPA linked to the same account -> rejected with `422 SAME_ACCOUNT`, because a hold, credit and capture on one account moves nothing and would only confuse statements.
- 2026-11-18 5.2: what happens when capture fails with a business error (HOLD_EXPIRED) after the credit -> CREDITED -> REVERSING, which reverses the payee credit and then releases the hold, because the payer's money never left and the payee must not keep it.
- 2026-11-18 5.2: what happens when a compensation step (reverse or release) is declined by the bank -> MANUAL_REVIEW, because the only way that happens is a payee who already spent the money or an inconsistent hold, and both need a person.
- 2026-11-18 5.2: risk step -> `allowAllRisk` behind a `RiskPort` interface, recorded as a `risk` step row, because Phase 6 replaces it and the saga shape should not change then.
- 2026-11-18 5.3: unknown versus transient for a closed connection -> `ServiceClient` now puts the undici cause code in `details.cause`; ECONNREFUSED / ENOTFOUND / EAI_AGAIN are TRANSIENT (nothing was sent), every other socket error is UNKNOWN, because the fixed table says a dropped connection may have done the work.
- 2026-11-18 5.3: status codes the fixed table does not list -> other 4xx are BUSINESS, 429 is TRANSIENT, other 5xx are UNKNOWN, because a 500 from the adapter can happen after the ledger committed.
- 2026-11-18 5.3: retries exhausted with only transient failures -> hold: DEBIT_FAILED, credit: CREDIT_FAILED then reversal, capture/release/reverse: park and retry later with backoff (`park_count`, `next_run_at`), because the first two can still be cancelled safely but the last three must eventually finish.
- 2026-11-18 5.3: retries exhausted and at least one attempt might have happened (any UNKNOWN row, or a STARTED row left by a crash) -> DEEMED with `deemed_step`, because guessing either way can lose or create money.
- 2026-11-18 5.3: how DEEMED resolves -> every `SWITCH_DEEMED_POLL_MS` the recovery loop asks `GET /banks/:bank/status/:txnId`; DONE continues forward, FAILED takes the business branch, missing or IN_PROGRESS re-sends the identical request once, and after `SWITCH_DEEMED_MAX_POLLS` it goes to MANUAL_REVIEW, because re-sending is safe (adapter idempotency) and the status call is the only source of truth.
- 2026-11-18 5.3: DEEMED for a hold or a capture too, not only for a credit -> yes, the same poller handles all three forward steps, because an unknown hold is just as unsafe to guess.
- 2026-11-18 5.3: what counts as a breaker failure -> TRANSIENT and UNKNOWN; OK and BUSINESS count as success because the bank answered; CIRCUIT_OPEN and BULKHEAD_FULL attempts are logged as TRANSIENT without calling the bank, because they provably did nothing.
- 2026-11-18 5.3: breaker and bulkhead state -> in memory per process, per bank, because they protect this process's calls; a restarted process starts CLOSED, which is the normal behaviour of a client-side breaker.
- 2026-11-18 5.4: lock primitive -> a lease (`lease_owner`, `lease_until`) plus `fence` on the `txns` row; acquiring always increments `fence`, and every step-log write and state change is `WHERE fence = ? AND lease_owner = ?`, because SQLite has no row locks and this lets two processes share switch.db safely.
- 2026-11-18 5.4: what a fenced-out writer does -> throws `LeaseLost`, logs a warning and stops without touching the row, because the new owner will redo the step and the adapter makes that safe.
- 2026-11-18 5.4: how chaos kills the process without Docker -> `SWITCH_CHAOS=true` enables `PUT /internal/chaos { crashAt }` (blocked by the gateway); the next saga to reach that boundary calls `process.exit(137)`. `scripts/stack.ts` gained `restartOnCrash`, which restarts the process like a Docker restart policy, because there is no `docker kill` here.
- 2026-11-18 5.4: chaos suite location -> `tests/e2e/phase-5.4.test.ts` (not `tests/chaos/`), because the gate runs e2e files by phase and needs the spawned stack.
- 2026-11-18 5.5: deterministic simulation -> `test/simulation.test.ts` runs the real `SagaEngine` against `FakeBankNetwork` with a `FakeClock`, a seeded PRNG for faults, latency, crashes and backoff jitter, and checks money invariants per seed; `SIM_SEED=<n> npm run sim:switch` replays one seed, because a failing seed must be reproducible exactly.
- 2026-11-18 5.5: load test tool -> `scripts/load-switch.ts` (Node, no k6) against a running stack, and a smaller in-gate load test in `phase-5.5`, because k6 is not installed and the gate must stay self-contained.
- 2026-11-18 5.5: staff tools -> `retry` (resume from `review_from`) and `reverse` (compensate what the switch recorded) on MANUAL_REVIEW only, both with a mandatory reason and an `ops_actions` row, because these are the only two moves that never need a ledger edit.
- 2026-11-18 5.5: retry after a bank declined a step -> not useful: the adapter stores 4xx outcomes per `(bank, txnId, step)` and replays them, so the case stays in MANUAL_REVIEW; the fix then belongs to bank operations (Phase 12), because changing the adapter contract is outside Phase 5.
- 2026-11-18 5.5: reverse after an unresolved DEEMED -> the tool first asks the bank; DONE refuses with `DEEMED_STEP_SUCCEEDED` (use retry), IN_PROGRESS refuses, an unreachable bank refuses with 503, because reversing a credit that actually happened would make the payee bank lose money.
- 2026-11-18 5.5: a hold the switch never learned about (unknown hold that went to review, then reversed) -> left to expire by the ledger hold sweeper (TTL `SWITCH_HOLD_TTL_SECONDS`, default 600 s), because the switch has no hold id to release.
